# `rest-cache` — tag-invalidated cache at the REST boundary

The cache layer that supports **selective invalidation**, which Grafbase Entity
Cache cannot. Sits between the gateway's REST extension / `funds-subgraph` and
the three REST services, caching `GET` responses in **Redis db 1** with a real
`tag -> keys` index.

```
AEM content change
        |
        v   POST /_invalidate {"tags":["account:acct-1001"]}
   rest-cache ──> SMEMBERS tag:account:acct-1001 ──> UNLINK those keys
        |
        v
  accounts / funds / policies REST
```

## Why this exists rather than using Grafbase Entity Cache

| | Grafbase Entity Cache | `rest-cache` |
|---|---|---|
| Key | `insurance-entitycache-<blake3 hex>` | `rc:accounts:GET:/accounts/acct-1001` |
| Key inputs | subgraph + **every request header** + entity repr | the request path |
| Reconstructible externally? | No — unsalted hash over unbounded header sets | Yes, trivially |
| Redis types | `string` only | `string` + **`set`** (the tag index) |
| Entity id in the payload? | **No** — `{"name":"Green Bond Income","currency":"GBP"}` | n/a, the key carries it |
| Delete API | **None** — the cache trait is `get`/`put` only | `POST /_invalidate` |
| Invalidation | TTL expiry only | selective, by tag |

`scripts/test-tag-invalidation.sh` asserts every row of that table on a live
stack, including running `SMEMBERS` against a Grafbase key and getting
`WRONGTYPE`.

## Redis layout (db 1)

```
rc:accounts:GET:/accounts/acct-1001            string   <upstream body>   EX 600
tag:account:acct-1001                          set      { rc:... }        EX 660
```

- `db 1` keeps these physically separate from Grafbase's own cache in `db 0`, so
  neither side's `FLUSHDB` can harm the other.
- Tag sets get `TTL + 60` so they always outlive the entries they track —
  otherwise a tag expires while its entries live on and become unreachable.

### Tag vocabulary

| Tag | Set when |
|---|---|
| `account:<id>` | a response contains that account, or is scoped to it |
| `customer:<id>` | a response contains an account or policy for that customer |
| `policy:<id>` | a response contains that policy |
| `fund:<id>` | a response contains that fund, **or an account/policy referencing it** |
| `collection:accounts` \| `collection:funds` \| `collection:policies` | list endpoints |

**Tags come from the response body, not the URL.** `GET /accounts` is tagged
with every account it contains, so invalidating one account correctly drops the
list too. A URL-only scheme would leave that list stale.

## Endpoints

Available on every listener (`:3101` accounts, `:3102` funds, `:3103` policies).

```bash
# what is this listener fronting?
curl -s localhost:3101/_health

# which keys carry a tag?
curl -s 'localhost:3101/_tags?tag=account:acct-1001'

# invalidate — this is what AEM would call
curl -s -XPOST localhost:3101/_invalidate \
  -H 'content-type: application/json' \
  -d '{"tags":["account:acct-1001","fund:fund-green-bond"]}'
```

Every proxied response carries `x-rest-cache: HIT | MISS | BYPASS`,
`x-rest-cache-key`, and `x-rest-cache-tags`.

`BYPASS` means **the route produced no tags, so it was deliberately not cached**
— caching something that cannot be invalidated is the exact failure this layer
exists to prevent. Add a branch to `tags.js` to make such a route cacheable.

## Configuration

| Env | Default | Notes |
|---|---|---|
| `REDIS_HOST` / `REDIS_PORT` | `redis` / `6379` | Valkey works unchanged — `SADD`/`SMEMBERS`/`UNLINK` are core RESP |
| `REDIS_DB` | `1` | keep off `0`, which is Grafbase's |
| `CACHE_TTL_SECONDS` | `600` | backstop behind real invalidation, not the freshness mechanism |
| `UPSTREAMS` | accounts/funds/policies | JSON `{ "<port>": { "name", "upstream" } }` |

### How it is wired in

Nothing in `schema.graphql` changes — it is regenerated by `schema-gen` and would
lose the edit. Instead `docker/gateway-entrypoint.sh` reads the upstreams from
env when it rewrites the baseURLs:

```
ACCOUNTS_UPSTREAM   http://rest-cache:3101   (was http://accounts-rest:3001)
POLICIES_UPSTREAM   http://rest-cache:3103   (was http://policies-rest:3003)
FUNDS_REST_URL      http://rest-cache:3102   (was http://funds-rest:3002)
```

Point them back at the REST services to **bypass the cache entirely** — useful
for A/B demos:

```bash
ACCOUNTS_UPSTREAM=http://accounts-rest:3001 \
POLICIES_UPSTREAM=http://policies-rest:3003 \
FUNDS_REST_URL=http://funds-rest:3002 \
  docker compose -f docker-compose.gateway.yml up -d
```

## ⚠️ Grafbase's entity cache sits in front of this

For the `funds` subgraph, Grafbase caches the `_entities` response in db 0.
**Invalidating a `fund:` tag here is not visible through the gateway until that
TTL expires** — the gateway never asks `rest-cache` again in the meantime.

`FUNDS_ENTITY_TTL` (default `5s`, applied by the entrypoint) keeps this short so
invalidation is demonstrable. Set `FUNDS_ENTITY_TTL=120s` to restore the original
entity-caching demo.

Accounts and policies are unaffected — they resolve through the REST extension
and were never entity-cached at all, so their invalidation shows through
immediately. **That contrast is worth demoing deliberately**: it is the clearest
illustration of why the cache had to move to a layer we own.

## Before production

This is a **proof of concept**. Known gaps, in rough priority order:

1. **`/_invalidate` is unauthenticated.** Anyone who can reach the port can flush
   the cache. Needs a shared secret or network policy.
2. **The cache key does not vary on identity.** Correct today — all callers share
   one service API key and every caller may see every account. The moment these
   calls carry a per-user or per-tenant credential, a path-only key becomes a
   **cross-user data leak**. Add the identity dimension to the key, or confirm the
   upstream response is identical for all callers.
3. **No stampede protection.** Invalidating a hot tag sends every concurrent
   request to the origin at once. Needs a single-flight lock.
4. **Redis failure returns 502.** It should fail open to the upstream — degraded
   latency beats an outage. It must never fail open to *stale*.
5. **Redis Cluster.** Hash-tag the namespace (`rc:{acct-1001}:...`) so an entity's
   entries and its tag set share a slot and `SMEMBERS`+`UNLINK` stay atomic.
6. **Tag granularity.** `accountTags` currently tags accounts with `fund:<id>` for
   every holding — deliberate over-invalidation. Right if `currentValue` tracks
   fund pricing; wasteful if only fund names/currency change. One line in
   `tags.js`.

## Demo-only change outside this directory

`mock-rest-apis/accounts/server.js` gained a `PATCH /accounts/{id}` route that
mutates the in-memory record. Without a way to change the data, an invalidation
demo can only prove "the key was deleted", not "stale content became fresh".
It is clearly marked `DEMO-ONLY` and nothing persists across a restart.
