# Calling REST APIs from Hive: do we need subgraphs?

**Audience:** engineering team
**Status:** findings from two working POCs in this repo
**Related:** [HIVE-EVALUATION.md](./HIVE-EVALUATION.md) (why Hive over Grafbase)

---

## TL;DR

**Hive Gateway can call REST directly, with no subgraph servers.** We already have
this working. It is a near-exact analogue of the Grafbase REST extension.

**Hive Router cannot.** It only speaks to federated GraphQL subgraphs over HTTP.
That single limitation is the entire reason our Router POC needs three extra
services and 161 lines of hand-written schema.

If the hand-written subgraph code is what bothers us, the fix is not a different
subgraph framework. It is choosing Gateway over Router.

---

## 1. The question

> Do we have to build GraphQL subgraphs in front of our REST APIs, or can the
> gateway call REST directly the way Grafbase did with its REST extension?

Worth asking, because our two POCs look very different in size:

| | `hive-poc` (Gateway) | `hive-router-poc` (Router) |
|---|---|---|
| Total services | 7 | 10 |
| **Subgraph servers** | **0** | **3** |
| REST mapping | generated from OpenAPI | 161 hand-written lines |
| Code we wrote | 483 lines | 730 lines |

---

## 2. Hive Gateway: yes, REST directly, no subgraphs

Our Gateway POC runs seven services and **not one of them is a subgraph
server**:

```
accounts-rest   funds-rest   policies-rest     <- the existing REST APIs
hive-gateway                                   <- calls them directly
valkey          invalidator                    <- caching
mesh-compose                                   <- build step, runs once, exits
```

The gateway calls the REST APIs in-process. The mapping lives in directives,
exactly like Grafbase.

### Side by side with Grafbase

| | **Grafbase** | **Hive Gateway** |
|---|---|---|
| Declare the endpoint | `@restEndpoint(name:, baseURL:, headers:)` | `transport: {kind: "rest", location:, headers:}` |
| Map a field to a route | `@rest(endpoint:, http: {GET: "/accounts/{{args.id}}"})` | `@httpOperation(subgraph:, path: "/accounts/{args.id}", httpMethod: GET)` |
| Who makes the HTTP call | REST WASM extension, in-process | Mesh REST transport, in-process |
| Subgraph servers needed | none | none |

A real field from our generated supergraph:

```graphql
account(id: String!): Account
  @httpOperation(
    subgraph: "Accounts"
    path: "/accounts/{args.id}"
    httpMethod: GET
  )
```

And the endpoint declaration:

```graphql
transport: [{
  subgraph: "Accounts"
  kind: "rest"
  location: "http://accounts-rest:3001"
  headers: [["X-Api-Key", "{env.ACCOUNTS_API_KEY}"]]
}]
```

### The one real difference from Grafbase

| | Grafbase | Hive Gateway |
|---|---|---|
| When | runtime | **build time** |
| Authored by | us, by hand in `schema.graphql` | **generated by Mesh from `openapi.yaml`** |

Grafbase: we hand-write `@rest` directives and the gateway loads them.

Hive: Mesh reads our OpenAPI specs and emits `@httpOperation` for us. We never
write those directives.

**This is arguably better for us.** The OpenAPI specs stay the source of truth,
and a spec change flows through on recompose instead of needing a hand edit. The
cost is a build step in CI. Nothing stops us hand-editing the supergraph, but it
is a generated artifact rather than a supported authoring surface, so we should
not.

---

## 3. Hive Router: no, and it cannot be made to

Hive Router consumes **federated GraphQL subgraphs over HTTP only**.

- No REST transport.
- No extension mechanism that adds one.
- Coprocessors hook request and response stages. They cannot synthesise
  REST-backed fields.

So with Router, something must turn REST into GraphQL first. In our POC that
something is three Yoga subgraph servers we wrote ourselves.

> **Related trap:** Router's config has a `cache` key that looks like the
> answer to caching and is not. It is in-memory only and caches parsing,
> validation, normalisation and query plans. It never stores response data and
> never removes an upstream call. Same category as Grafbase's
> `operation_caching`, which we already proved does not cut REST load.

---

## 4. Where the Router POC's complexity actually is

A common assumption is that GraphQL Yoga is the heavy part. It is not.

| File | Code lines | What it is |
|---|---|---|
| Three hand-written schemas | **161** | the REST-to-GraphQL mapping |
| REST client | 25 | fetch wrapper |
| Yoga bootstrap | 67 | server startup |
| Cache wiring | 59 | Redis response cache |
| Composer | 39 | subgraph SDLs to supergraph |
| Invalidator | 164 | purge API |

**Swapping Yoga saves 67 lines and costs us the plugin that makes caching
cheap.** Those 59 lines of cache config only work because
`@envelop/response-cache-redis` plugs into Yoga. Replace Yoga with a thinner
server and we hand-roll cache lookup, write-back, tag maintenance and
invalidation ourselves.

**The 186 lines of schema plus REST client are the real weight**, and they exist
only because Router cannot call REST.

## 5. Options if we keep Router

### Option A: generate the schemas instead of writing them ✅ partly verified

`@omnigraph/openapi` ships `loadGraphQLSchemaFromOpenAPI`, which returns a fully
**executable** GraphQL schema straight from an OpenAPI file. No resolvers.

Verified against our own accounts API:

```
Query fields generated : accounts, accounts_by_id, customers_by_customerId_accounts
Query executed         : returned real data from localhost:3001
Resolvers written      : zero
```

This would remove the 161 schema lines and, more importantly, remove schema
drift between our OpenAPI specs and our GraphQL layer.

> ⚠️ **Not yet verified.** That generated schema is not a federation subgraph. It
> has no `@key` and no `_entities`, so Router cannot join across the three. We
> would layer that on with `@graphql-tools/federation`. Estimated ~50 shared
> lines replacing 186 hand-written ones, but this is a spike, not a plan.

### Option B: run Hive Gateway as each subgraph

No resolvers, and caching becomes native Gateway config rather than plugin
wiring. But three Node gateways at 141 MB each, and we inherit the Gateway
cache's weaknesses that the Router POC was specifically built to avoid.

### Option C: replace Yoga with something lighter

`graphql-http`, Apollo Server, or a non-JS server. This is the literal answer to
"what can replace Yoga" and the worst option. We would lose the response-cache
plugin and gain nothing but a slightly smaller bootstrap.

### Option D: drop Router

Our Gateway POC already does this. One gateway, zero subgraph servers, zero REST
mapping code, caching as a config block.

---

## 6. The honest trade-off

Router is not useless here. It won on two things we measured:

| | Gateway POC | Router POC |
|---|---|---|
| Warm cache hit | 2.4 ms | **2.6 ms** (comparable) |
| Router image size | 141 MB | **32.5 MB** |
| Cache tags | flat keys + `SCAN` | **real Redis SETs + `SMEMBERS`** |
| Invalidation cost | O(total keys) | **O(tag size)** |
| Colons in cache keys | **break invalidation silently** | safe |
| Partial cache reuse | ❌ whole response or nothing | ✅ **2 REST calls instead of 5** after a purge |
| `Policy.linkedFunds` | ❌ not possible | ✅ one line |
| Services to operate | **7** | 10 |
| REST mapping code | **0 lines** | 161 lines |

**The critical caveat:** every cache win in the Router column came from putting
the cache *inside the subgraphs*, not from Hive Router. Router contributed zero
caching. We could get the same cache mechanics in any architecture that has a
subgraph layer to put them in.

---

## 7. Recommendation

**For this use case, Hive Gateway.** It does what we originally liked about
Grafbase, calling REST directly from directives with no subgraph servers, while
fixing the thing Grafbase could not do: caching actual response data with keys
we control and invalidation we can trigger.

**Choose Router only if** we expect real GraphQL subgraphs in future regardless
of this project, or we need the better cache mechanics badly enough to own three
more services. In that case, do Option A first so the OpenAPI specs stay the
source of truth.

### Suggested next step

Spike Option A, generated schema plus federation wrapper. It is the only option
where the estimate is not trustworthy, and it decides whether Router is viable
without a maintenance burden.

## Appendix: questions we should expect

**"Isn't the build step a downside versus Grafbase's runtime directives?"**
It is a CI step, and it buys us generated-from-spec mapping instead of
hand-written directives that can drift. Net positive for us.

**"Can we hand-write the `@httpOperation` directives like Grafbase?"**
Technically the gateway only reads the supergraph, so yes. But it is a generated
artifact, not a supported authoring surface, and hand edits are lost on the next
recompose.

**"Will Hive Router ever support REST or caching?"**
Response caching is an open RFC ([router#312](https://github.com/graphql-hive/router/issues/312)),
design stage only. REST is explicitly out of scope; the docs direct you to Mesh
or Gateway for non-GraphQL sources.

**"Why does the Router POC cache in the subgraphs rather than the router?"**
Because Router has nowhere to put a cache. That placement turned out to be
better anyway: it caches the router's own entity fetches and allows partial
reuse across a federated query.

**"How much work to switch from Router to Gateway?"**
None. Both POCs are built and verified. `hive-poc` is the Gateway one.
